Clockwerk

Schedule broadcasts, commands, restarts and events from an in-game GUI — with cron, missed-run policies and a store that survives a crash. For Paper 1.21+ and Folia.

Paper 1.21+ Java 21 Folia Cron SQLite / YAML

Clockwerk runs things on a schedule and does not lose track of it. Announcements, console and player commands, server restarts and bossbars are all scheduled from an inventory GUI — no config file required, though everything is editable there too. Schedules can be a one-off moment, a daily or weekly wall-clock time, a fixed interval, or a full five-field cron expression.

The part most schedulers get wrong is what happens when the server was off when a task was due. Clockwerk stores the next run, notices the mismatch on startup, and lets you decide per task: skip it, run it once on startup, or replay every run it missed (capped). A nightly restart that did not happen is a decision, not a surprise.

What you get

  • Five task types — broadcast, console command, player command, restart and bossbar.
  • Five schedule kinds — once, daily, weekly, interval and cron.
  • Missed-run policies — skip, run on startup, or catch up, chosen per task.
  • Full in-game GUI — create, edit, clone, enable, disable, delete and review tasks, plus an upcoming list and an execution history.
  • Cron, built in — five fields, ranges, steps, lists, month and day names and the classic Vixie day-of-month/day-of-week rule.
  • Bossbar restarts — warn before a run with as many countdown offsets as you like.
  • Two storages — SQLite by default (keeps history and survives a crash), or a hand-editable tasks.yml.
  • Multilingual — English, Spanish, German, French, Italian, Dutch, Polish, Brazilian Portuguese and Russian.
  • Paper & Folia — one jar, both platforms, chosen at runtime.
  • Developer friendly — a free Java API with cancelable events, plus PlaceholderAPI placeholders.

Setup

  1. Drop Clockwerk.jar into your plugins/ folder.
  2. Start the server. It creates plugins/Clockwerk/ with config.yml and the lang/ folder.
  3. Run /cw in-game to open the GUI and create your first task, or grant permissions — see Permissions.
Where things go. The plugin JAR sits in plugins/. Everything you edit lives in plugins/Clockwerk/: config.yml, lang/, and the database file clockwerk.db (or tasks.yml if you switch storage).
Reloading. After editing config.yml or a language file, run /cw reload — it re-reads the config, the translations and every task in place. No restart needed.

Permissions

Every node is standard op, so operators have them out of the box and a non-operator has none until a permissions plugin grants one. This is the ordinary Bukkit contract, so the server stays in charge of who may do what.

NodeDefaultWhat it allows
clockwerk.adminopEverything, through its children below.
clockwerk.manageopCreate, edit, clone and delete tasks.
clockwerk.runopRun a task by hand, and use the GUI buttons that act on tasks.
clockwerk.reloadopReload the configuration and language files.
clockwerk.nextopSee the upcoming runs and open the GUI.
Shaping access by role. clockwerk.admin grants all of the above at once. Grant or revoke the individual nodes in your permissions plugin if you want somebody to see the schedule without being able to change it.

Schedules

A task has one schedule, chosen from five kinds. Wall-clock schedules are read in the timezone set in config.yml.

KindFiresStored form
OnceA single date and time, then never again.once:2026-12-31T23:00:00Z
DailyEvery day at a fixed wall-clock time.daily:04:00
WeeklyEvery week on a fixed day and time.weekly:SUN:04:00
IntervalEvery N minutes, counted from an anchor.interval:15:1735689600
CronA five-field cron expression (see Cron).cron:*/15 * * * *
Why interval has an anchor. "Every 15 minutes" needs a fixed starting point, or two servers — and the same server across a restart — would broadcast at different moments. The runs fall on anchor + n × gap, so the phase never drifts. The anchor is set when the task is created and stored as epoch seconds.
Timezones. timezone: "SERVER" uses whatever the host calls local time, and most hosts call it UTC. If a daily 04:00 task fires at eight in the evening, that line is why — set it to the zone you actually mean, e.g. "Europe/Madrid".

Cron

Clockwerk speaks classic five-field cron: minute hour day-of-month month day-of-week. Pick the Cron schedule kind and type the expression.

The fields

FieldValuesNotes
minute0–59
hour0–2324-hour clock.
day-of-month1–31
month1–12 or JAN..DECNames are case-insensitive.
day-of-week0–7 or SUN..SAT0 and 7 are both Sunday.

Syntax

TokenMeans
*Every value in the field.
5Exactly that value.
1-5An inclusive range.
*/15Every 15th value from the field's minimum.
1,15,30A list of any of the above.

Examples

ExpressionFires
0 4 * * *Every day at 04:00.
*/15 * * * *Every 15 minutes.
0 9-17 * * 1-5Every hour on the hour, 09:00–17:00, Monday to Friday.
0 0 1 * *Midnight on the first of every month.
0 0 1 * MONThe first of the month and every Monday (see below).
30 23 * * 0Every Sunday at 23:30.
The Vixie rule. When both the day-of-month and the day-of-week fields are restricted, classic cron treats a day as matching when either side matches, not both. So 0 0 1 * MON fires on the first of every month and every Monday. Clockwerk follows this on purpose rather than "fixing" it — it is the behaviour people rely on.

Task types

What a task does when it fires. The payload is the message, command or bossbar title it uses.

TypeWhat it doesPayload
BroadcastSends a message to everyone online, console included.The message text.
Console commandRuns a command as the console. An unknown command is recorded as a failure, so it is visible in the history.The command, with or without a leading slash.
Player commandRuns a command as every online player.The command, with or without a leading slash.
RestartRestarts the server. Falls back to a clean shutdown if the platform refuses the restart.None.
BossbarShows a bossbar to the whole server for a number of seconds.The title text, plus a duration.
Colours. All text uses legacy colour codes with & and hex with &#RRGGBB — for example &cRestarting &#FFAA00soon.
Warnings. Any task can have warning offsets (in seconds) so players are told before it runs — for example 600, 60 and 10 for ten minutes, one minute and ten seconds before. Warnings fire once each, largest offset first.

Missed runs

When the server comes back up, Clockwerk compares each task's stored next-run against now. If the run was due while the server was off, the task's policy decides what happens. A task that was not due is untouched, and a paused task is never caught up.

PolicyWhat happens
Skip (default)Nothing is run. The next run is recomputed from now, so the missed occurrence stays missed. A nightly restart that did not happen stays did-not-happen.
Run on startupExactly one run: the earliest missed occurrence, fired once the server has finished starting. The following occurrences are not pulled forward — which is what stops a morning boot from turning into a restart loop.
Catch upEvery missed occurrence, oldest first, capped by engine.catchup-cap so a month of downtime cannot flood the server in one tick.
Why a delay. Catch-up runs wait a couple of seconds after startup, so a backlog cannot fire in the same tick that is still bringing worlds up.

Configuration

Everything lives in plugins/Clockwerk/config.yml. Edit it, then run /cw reload.

KeyWhat it does
langLanguage for all messages. Options: en, es, de, fr, it, nl, pl, pt-br, ru.
timezoneThe zone every wall-clock schedule is read in. "SERVER" uses the host's local time (usually UTC); write an explicit zone like "Europe/Madrid" if you mean it.
storage.typesqlite (default) keeps history and remembers the next run through a crash. yaml uses a hand-editable tasks.yml, but history does not survive a restart.
history.retention-daysHow long execution history is kept (SQLite only). 0 keeps it forever. Default 30.
engine.catchup-capThe most runs a CATCHUP task may replay at startup. Default 10.

API

Getting started

Hook another plugin into Clockwerk — register a task from your own code, or react when one runs. The API is free to use.

The API is a small, self-contained jar you compile against. At runtime you obtain it from the Bukkit ServicesManager, so you can also ask whether Clockwerk is installed instead of crashing with a ClassNotFoundException. Nothing from the plugin's internals is exposed.

Add the dependency

Compile against clockwerk-api with provided scope, so it is never bundled into your own jar. It isn't on Maven Central; download it from the API downloads page.

Maven — once the jar is in a repository you can resolve:

<dependency>
  <groupId>dev.mugi</groupId>
  <artifactId>clockwerk-api</artifactId>
  <version>1.0.0</version>
  <scope>provided</scope>
</dependency>

If it isn't published to a repository you use, install the downloaded jar into your local one:

mvn install:install-file -Dfile=clockwerk-api.jar \
  -DgroupId=dev.mugi -DartifactId=clockwerk-api \
  -Dversion=1.0.0 -Dpackaging=jar

Gradle — drop the jar in libs/ and point at it directly:

dependencies {
    compileOnly files("libs/clockwerk-api.jar")
    // or, once it is in a repository:
    // compileOnly "dev.mugi:clockwerk-api:1.0.0"
}

Declare it in plugin.yml

The server needs to know your plugin uses Clockwerk so it can load the classes at runtime.

depend: [Clockwerk]
# or, if Clockwerk is optional:
softdepend: [Clockwerk]

Use it

ClockwerkAPI api = Bukkit.getServicesManager().load(ClockwerkAPI.class);
if (api == null) {
    getLogger().warning("Clockwerk is not installed.");
    return;
}

// Read what is scheduled
api.getTasks().forEach(view ->
        getLogger().info(view.name() + " next runs " + view.nextRun()));

// Register a task from your own plugin
ClockwerkTaskDraft draft = ClockwerkTaskDraft.builder()
        .id("my_plugin_daily")
        .name("Daily reward")
        .type(TaskType.CONSOLE_COMMAND)
        .schedule(ScheduleKind.DAILY, "04:00")
        .payload("rewards give all")
        .build();
api.createTask(draft);

ClockwerkAPI

The interface you get from Bukkit.getServicesManager().load(ClockwerkAPI.class). Every method must be called from the main thread.

MethodReturnsWhat it does
createTask(ClockwerkTaskDraft)ClockwerkTaskViewRegisters a task from a draft. Throws IllegalStateException if the id is already taken.
getTask(String)Optional<ClockwerkTaskView>One task by id.
getTasks()Collection<ClockwerkTaskView>Every loaded task.
runTask(String)booleanRuns a task now, as if an admin clicked "run now". Returns whether the task existed.
setTaskEnabled(String, boolean)booleanArms or pauses a task. Returns whether the task existed.
deleteTask(String)booleanRemoves a task. Returns whether it existed.
getUpcoming()List<UpcomingRun>The next runs across all tasks, soonest first.

The ClockwerkTaskView record

An immutable, read-only view of a loaded task. It holds only definition data and the run times, never the store's internals.

AccessorTypeWhat it is
id()StringThe task id.
name()StringThe display name.
type()TaskTypeWhat the task does.
scheduleKind()ScheduleKindThe schedule's kind.
scheduleDetail()StringA short description of the schedule parameters.
payload()StringThe message, command or bossbar title.
missedPolicy()MissedPolicyWhat happens to runs the server slept through.
enabled()booleanWhether the task is armed.
lastRun()Optional<Instant>When it last executed.
nextRun()Optional<Instant>When it will next execute.

The ClockwerkTaskDraft

What you build to register a task. The schedule is set from a ScheduleKind plus the parameters that kind needs.

KindParameters
ONCEAn ISO instant, e.g. "2026-12-31T23:00:00Z".
DAILY"HH:mm".
WEEKLY"DAY:HH:mm", e.g. "SUN:04:00".
INTERVALMinutes, e.g. "15".
CRONA five-field expression.

Events

EventWhat it's for
TaskExecuteEventFired before a task's action runs. Cancellable — cancel it and the run is dropped (and recorded as skipped).
TaskCompleteEventFired after the action runs, whether it succeeded or threw. Record metrics or mirror a restart into Discord here.
TaskSkippedEventFired when a run is dropped — by a listener cancelling it, or by the missed-run policy. Carries the reason.

Listening

@EventHandler
public void onExecute(TaskExecuteEvent event) {
    // Hold a restart during a tournament, for example
    if (event.task().type() == TaskType.RESTART
            && tournamentIsRunning()) {
        event.setCancelled(true);
    }
}
